# AGENTS.md

Guidance for AI assistants working on **Git Island**.

## Publication authority (mandatory)

Default workflow: update from `origin/main`, implement on a `jb/` branch, validate,
commit, push that branch, and open a PR. Leave the PR open for the user.

- **Merge requires an explicit user request for that PR.** A request to fix,
  implement, check, prepare, or open a PR does not authorize merging, enabling
  auto-merge, pushing directly to `main`, or bypassing review/CI requirements.
- **Website deployment belongs exclusively to CI after a PR merges into `main`.**
  Never deploy directly to Cloudflare from a local checkout, another branch,
  a CLI, API, dashboard, or tool. This includes `npm run deploy`, `cf deploy`,
  `wrangler deploy`, prebuilt uploads, and direct rollbacks. Use local builds
  and previews for validation; correct production through a reviewed PR.
  Do not rerun an older deployment job to publish a stale revision.
- **Homebrew, DMG, and TestFlight each require an explicit user publication request.**
  Authorization for one channel does not authorize the others or future releases.
  A site merge does not authorize any app release. If the requested channels or
  release are ambiguous, prepare the artifacts and ask before publication.
- Without that request, keep release work local or in a PR: no TestFlight binary
  upload, tester distribution, GitHub release creation (including drafts), DMG
  asset upload/replacement, or publication of a cask update to the Homebrew tap.
  Homebrew changes also go through a PR in `nomdelasociete/homebrew-tap`; never
  push directly to its default branch. Never add automatic app-release publishing
  as a side effect of a website or installation task.
- Before an authorized merge or publication, fetch again and inspect pending
  changes and deployments. Compare the intended revision with what production
  actually serves. If production contains changes absent from `main`, or a newer
  deployment could be replaced, report the discrepancy and reconcile it through
  a PR before proceeding. Never silently overwrite work from another chat/branch.
- Report preparation, upload, processing, distribution, and deployment separately.
  Claim a website publication only after CI deployment succeeds and the public
  assets match the intended revision. Claim an app release only after verifying
  the requested channel's artifact and availability; upload alone is insufficient.

## What this is

Native macOS 26 menu-bar utility: a **notch-adjacent Dynamic Island** showing counters for the signed-in user's GitHub PR inbox — `blocked`, `waiting`, `testing`, `ready`. Notch MacBooks only.

- **Bundle IDs:** Release/TestFlight `com.nomdelasociete.GitIsland`; Debug `com.nomdelasociete.GitIsland.dev`
- **Repo:** https://github.com/nomdelasociete/git-island
- **Stack:** Swift 6.2, Xcode macOS app target generated by XcodeGen, SwiftUI + AppKit (`NSPanel`)
- **North star:** Apple-native, calm, iOS Dynamic Island–style — not flashy third-party notch clones

## Build and run

Always build yourself; do not tell the user to run commands unless blocked.
Prefer the Xcode project for development so Xcode owns the app bundle,
DerivedData, and local signing.

```sh
xcodegen generate --spec project.yml
xcodebuild -project GitIsland.xcodeproj -scheme GitIsland -destination 'platform=macOS' build
```

Use compile-only validation when you do not need to launch the app:

```sh
xcodebuild -project GitIsland.xcodeproj -scheme GitIsland -destination 'platform=macOS' build CODE_SIGNING_ALLOWED=NO
```

Do **not** launch the app from Codex/terminal unless the user explicitly asks.
The user normally launches from Xcode; launching another copy can create duplicate
instances and unexpected macOS credential prompts. For most code changes, use
compile-only validation and leave runtime visual validation to Xcode.

Debug builds are **Git Island Dev** (`com.nomdelasociete.GitIsland.dev`).
Release archives keep **Git Island** (`com.nomdelasociete.GitIsland`) for
TestFlight. Keep these identities separate, including Keychain groups and
preferences. Never override a local Debug build with the production bundle ID.

The local helper only accepts Debug and defaults to ad-hoc signing:

```sh
./script/build_and_run.sh build    # compile only
./script/build_and_run.sh          # launch Dev only, with user authorization
```

- Xcode dev output: `~/Library/Developer/Xcode/DerivedData/.../Build/Products/Debug/Git Island Dev.app`
- Script output: `DerivedData/Build/Products/Debug/Git Island Dev.app`
- Use Xcode archives for TestFlight releases.
- Never sign standalone local bundles with Apple Development; use Xcode for
  that signing mode.
- Validate a TestFlight installation by checking its build number, Apple
  TestFlight signature, and the running executable path under /Applications.
  A successful upload or TestFlight's displayed version alone is insufficient.
- Debug-only settings: `GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_OAUTH_CLIENT_ID`. Tokens are fallbacks when no stored credential exists; explicit sign-out suppresses them across restart.

Ordinary tests run through `swift test --skip RelayLiveAcceptanceTests`; the Xcode scheme has no test target.

## Notch layout (critical)

Use **notch-adjacent wings**, not full menu-bar auxiliary width.

macOS `auxiliaryTopLeftArea` / `auxiliaryTopRightArea` span the **entire** left/right menu bar (e.g. 0→790px and 1010→1800px on a 16" MacBook). Using full auxiliary width pushes counters to screen edges and breaks the design.

Correct geometry (`IslandPanelController`):

- `wingWidth` ≈ 92pt each side of the physical notch gap
- `originX = leftArea.maxX - wingWidth`
- `width = leftWing + gap + rightWing` (~404px)
- Expanded counters: ready on the left wing; blocked/waiting/testing on the right wing
- Compact surface is the notch only (plus `compactOutlineOutset`); wings are used only while expanded
- Black surface is **continuous across the notch gap**

Panel frame:

- `y = screen.frame.maxY - height` — **top anchored** at screen top
- The top edge invariant is absolute: while visible, `panel.frame.maxY`
  must stay at the screen top/notch top on every frame. No hover, group switch,
  collapse, or animation may show wallpaper between the screen top and island.
- Compact: `panelFrameSize.height == visibleHeight + outlineLaneRoom`, where
  `visibleHeight == collapsedHeight`. The lane room only holds the outline
  lanes stacked past the outset (0–10pt) and is not hit-testable.
  Do not keep a tall invisible window while collapsed.
- Expanded: separate the AppKit host height from the visible SwiftUI surface.
  `panelChromeHeight` may retain the maximum height needed for the current
  expanded hover session so the `NSPanel` frame stays stable. `chromeHeight` /
  `visibleHeight` remain the actual visible content height.
- `NotchIslandShape.bodyBottomY` must use `chromeHeight`, not the retained host
  height. Hit-testing, pointer tracking, and collapse geometry must use
  `visibleHeight`, not the retained host height.
- When switching between groups (e.g. blocked ↔ testing or notch center ↔ a
  counter), never shrink/reposition the `NSPanel`. Animate only the SwiftUI
  surface/content; keep the host top-anchored until collapse retention clears.

## Interaction model

- **No PRs → no island** (iOS Live Activity rule: nothing live, nothing shown)
- Compact: no counters. An outline hugs the notch; each status owns a
  share of it proportional to its PR count (left→right: ready, blocked,
  waiting, testing) and draws one lane per PR there. Lane 0 hugs the notch,
  extra lanes stack outward; past 5 PRs they fuse into one band 5 lanes
  thick. Equal lane counts stay aligned across a boundary; extra lanes bend
  onto the last shared lane. Keeps the menu bar free for macOS 27 status items.
- Hover notch → expand all; once expanded, hover counter → select group
- Click counter → toggle; click outside / pointer leave ~280ms → collapse
- The outline stays visible while expanded and morphs with the surface;
  its lanes fold onto the innermost one as the island widens.
  Morph is Dynamic Island–style: widen then drop on open, rise then narrow
  on close, width and height on separate springs.
- New PR / status change after the initial refresh → boundaries spring to
  the new proportions (slight wobble), a white sheen runs along the ring from
  the old segment to the new one (whole ring for a new PR), and the
  destination segment briefly thickens. Crazy mode: double sheen, stronger
  thickening, and waves of the status color radiating from the outline
- AppKit coordinates: origin **bottom-left** — counter hit-testing must use `y >= height - topBandHeight`
- Pointer polling while expanded (global monitors need Accessibility permission)
- Testing counter spinner: only when `count > 0` for `.testing`, **not** on global `isLoading`

## GitHub data

Buckets mirror the PR inbox via search (no private inbox API):

- **blocked** — drafts, changes requested, failing checks, merge conflicts
- **waiting** — review required, including PRs waiting for the signed-in user's review
- **testing** — pending checks
- **ready** — approved + green checks

Scope: authenticated user's authored open PRs plus open PRs directly requesting
their review. Review-requested PRs remain visible even if they live in another
repository. If the only missing requirement is the signed-in user's review, keep
the PR in `waiting` with `needsUserAction`; reserve `blocked` for real red
blockers. Draft PRs are intentionally excluded from most test flows because the
app filters them out of the live inbox.

Ready PR rows can merge using GitHub's viewer/repository default merge method.
The button first changes to a same-place confirmation state; the REST merge call
uses the displayed head SHA, then refreshes the inbox.

A mergeable PR only counts as `ready` when the viewer's `viewerPermission` is
`WRITE`, `MAINTAIN` or `ADMIN`; otherwise it waits with "Waiting for
maintainer". When `viewerCanMergeAsAdmin` is true and only branch protection
blocks the PR (`BLOCKED`, not changes requested, failing checks or conflicts),
the row offers a press-and-hold "Bypass" button that uses the same REST merge.

Without live enrollment, refresh is local-only and adaptive. Use prompt event-driven refreshes, capped by
a short minimum spacing, for app focus, island interaction, wake, network return,
and merge; temporary 20-30s bursts for fresh activity or running checks; then
fall back to the saved idle interval (`UserPreferences`). Optional enrolled relay
connections trigger fresh GitHub reads; polling remains the fallback. The hosted
service is separate from this client. Document changes to trust boundaries and
data flows in PRIVACY.md; do not introduce new services without a product decision.

Auth: GitHub OAuth **device flow** on first launch. Client ID in `publishedClientID`. Tokens in Keychain.

## Design rules

- Compact: flush to top, rounded **bottom** corners only, hugging the notch with the status outline
- Expanded: same top band + body; height fits content
- No wallpaper showing through notch gap — solid black across wings + gap
- No redundant headers ("READY / Ready to merge")
- Arrival ripple is decorative only: overlay, non-hit-testing, no layout change,
  and respects Reduce Motion
- Verify visually on real notched hardware before shipping UI changes

## Hover regression postmortem

This app already had a bad hover regression caused by treating AppKit window
height and SwiftUI island height as the same thing. The broken implementation
made `panelFrameSize.height` follow the currently selected list height. Moving
from one hover target to another (red ↔ blue counters, notch center ↔ group,
all PRs ↔ one group) changed the `NSPanel` height, which recalculated
`y = topY - height`. The visible result was unacceptable: the island detached
from the top of the screen, corners flickered between square and rounded, and
the content appeared to jump instead of morphing like a Dynamic Island.

Do not repeat that mistake. For hover and expansion work, preserve these
invariants before judging the change done:

- The black surface must remain physically attached to the screen top/notch at
  every frame.
- Switching hover targets must not change the `NSPanel` top edge.
- A shorter selected list must shrink only the drawn SwiftUI surface, not the
  expanded-session host frame.
- A taller selected list may grow the expanded-session host once, top-anchored,
  before/while the visible surface expands.
- Transparent host area outside `visibleHeight` must not capture clicks.
- If you only ran compile-only validation, say so. Do not claim a visual hover
  or animation bug is fixed without either testing on notched hardware or being
  explicit that runtime validation is still pending.

Minimum visual checks for this class of bug:

- Hover from outside → notch center → blocked counter → testing counter → back.
- Hover directly from blocked to testing and testing to blocked.
- Repeat with unequal list heights, e.g. 2 blocked PRs and 1 testing PR.
- Confirm there is never a top gap, never a square-corner flash, and never a
  full-notch-height vertical jump.

## What not to do

- Do not span the full menu-bar auxiliary width for the island panel
- Do not use a permanent fixed max-height invisible panel (click-through bugs)
- Do not make the `NSPanel` frame height follow each selected group while
  expanded; that reintroduces the top-detach hover jump
- Do not use Apple Development cert for `./script/build_and_run.sh` local `.app`; use Xcode for Apple Development signing
- Do not tie testing spinner to `store.isLoading`
- Do not trigger arrival ripple on first load; only trigger it when new PR IDs
  appear after a previous refresh
- Do not invert AppKit Y coordinates in hit tests
- Do not add markdown docs or drive-by refactors unless asked
- Do not expand scope (repo picker, Sparkle, tests) unless explicitly requested

## PR workflow for this repo

- Always update the worktree before coding (`git fetch --all --prune` and inspect `git status -sb`).
- Use `jb/` branch names.
- For PRs meant to test the app's live inbox or visual arrival effects, create
  a **non-draft** open PR and do not merge it unless explicitly asked.
- If `gh pr merge` reports that local `main` is already used by another worktree,
  check the PR state on GitHub before retrying; the remote merge may already have
  succeeded.

## Testing changes

1. `xcodegen generate --spec project.yml`
2. `xcodebuild -project GitIsland.xcodeproj -scheme GitIsland -destination 'platform=macOS' build`
3. Launch from Xcode when visual validation is needed, then confirm the Debug app runs (`pgrep -x "Git Island Dev"`). Check its executable path as well; a running TestFlight copy is not validation of the Debug build.
4. On notched Mac: hover expand/collapse, counter positions, click-through below compact bar, group switch without notch jump
